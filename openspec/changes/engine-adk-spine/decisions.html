Why "several models" reshapes the plan

Today every agent inherits the caller's model. The moment agents pin their own, three things that were latent become real — two of them are decisions (D4, D5), one is a bug to fix on the way.

Already true · must survive

A delegated child resolves its own spec.Model → its own credential, its own client (delegation.go). On the spine: one ChatModelAgent + one WrapModel per child. The contract suite gains a case for it.

Latent bug · F-26

The model cache key is provider/model/token-hash — no BaseURL. Add a second OpenAI-compat provider exposing the same id (say glm-5.3-flash on Ollama cloud and on z.ai) and the second call silently reuses the first provider's client. Pinned as a characterization test today; the ADK path keys on provider + baseURL + model + token.

Consequence

"Reasoning effort" and "which model writes the summary" stop being global settings and become per-model questions — the subject of D4 and D5.

D1

Delegate surface: one tool per agent, or one dispatch tool?

Both are the same underneath — an ADK AgentTool over the child's ChatModelAgent, fold-back = the child's final answer. The difference is what the model sees and what can go wrong.

Example · the dispatch tool (today) on a mid-tier root 
{"name": "delegate_agent",
 "arguments": {"agent": "reseach-agent",   ← typo
               "task": "Find the 2026 INR/USD drivers; write sources/evidence-inr.md"}}
engine: unknown agent "reseach-agent"
(configured: adversarial-reviewer, builder-agent, planner-agent,
 research-agent, reviewer-agent, writing-agent)

The model reads the error and retries: one wasted step — the 13.6k fixed overhead re-sent for nothing, on the root's model tier.

Example · per-agent tools (proposed) 
{"name": "research_agent",
 "arguments": {"task": "Find the 2026 INR/USD drivers; write sources/evidence-inr.md"}}
# tool description the root reads (generated from the registry)
research_agent — Gathers, evaluates, and synthesizes evidence for a
self-contained research task. Runs on ollama/gemini-3-flash-preview.
Must use tools (require_tool_use). Works inside the active ward.

No agent-name argument to get wrong. The model is part of the menu, so the root chooses by capability and tier.

Trade-off

Six delegatable agents → six schemas (~650 tokens/step) vs. one routing table (~350). Net cost ≈ +300 tokens/step — against a 13.6k overhead, and slice 1's reduction trims menus anyway.

Prompt churn

Seeds and the persona mention delegate_agent by name in places; they become advisory, not broken. Zero churn is the only argument for the dispatch tool.

Recommendation

Per-agent tools. ADK-native (adk.NewAgentTool), removes a failure class the solar run already paid for, and makes the multi-model roster visible to the root.

Legacy retention: how long does the old loop stay?

Both paths already have to pass the full conformance suite during the transition. The question is only what happens after the default flips to adk.

Default flips to adk. contracttest green (incl. delegation), task verify green, archived.
Day 2
Solar re-run on glm-5.3-flash: the builder writes 127 lines but never calls the skill tool — clean-code never loads. Tests can't see model behaviour; a live run can.
+10 seconds
engine_loop: legacy in config.yaml, restart air. Same binary, old loop, bodies back in the prompt. Research continues.
Day 14
Root cause fixed (prompt nudge to load skills), three clean runs. Follow-up change deletes the legacy loop and the flag.
Option A · keep one soak cycle

Revert = a config line. Cost: two run paths kept honest by the suite for one cycle; the package carries ~400 lines that are already scheduled to die.

Option B · delete at archive

Cleaner tree. Revert = git revert of a multi-slice change + rebuild + redeploy — while a ward run is broken.

Recommendation

Option A. The risk this change carries is behavioural (skills-as-tool, sticky nudges), and behaviour only shows in live runs.

D4

Summarizer: which model compresses the history?

In-run summarization (roots and children) is one extra model call that ingests nearly the whole history. With several models, "use the run's model" is a choice — and often the wrong one.

Example

A root on gpt-oss:120b-cloud carries five shell dumps (25–38 KB each, as in the solar run). It crosses your compaction.max_context_tokens: 128000. The summary call sends ~110k tokens to… which model? And a child on the same 120b model hits its own threshold three steps later.

SummarizerSummary qualityCost · latencyPrivacyWhen it's right
the run's own modelbest fidelity — it read everything in its own framea 110k-token call at the run's tier; a 120b model compressing its own dumpssame as the runsmall runs; a single-model fleet (today)
ollama/glm-5.3-flash:cloudgood on structure; may blur exact figuresfast, cheapest tier you run (the analyst's tier)leaves the devicethe default — mechanical compression
ollama/llama3.1:8b (local)weakest at preserving numbers, paths and citationsfree, on-device, 128k windownever leaves the deviceprivacy-max wards; non-research work

The built-in keeps the most recent user messages intact (default 30k tokens, PreserveUserMessages), so the facts closest to the work survive whichever model writes the older summary.

Shape

compaction.summarizer: ollama/glm-5.3-flash:cloud — one global default for roots and children; empty = the run's own model (today's behaviour). Children inherit the global, never their own expensive model by accident.

Recommendation

Cheap cloud flash as the default summarizer. Local 8b if the ward's content must stay on-device — at a known quality cost for research runs.

D6

Plan events: adopt plantask now, or leave it to S2?

The handoff maps S2's plan_step_* events to the plantask middleware. It fits the spine — but it brings its own vocabulary, and S2 already has one.

Example · two plan vocabularies in one run

S2 · the analyst's plan

# events

plan_step_done     {step: 3, status: ok}

# consumer
the mockup's Plan row (run-legibility)

plantask · task files

# 4 tools injected on every step
TaskCreate {subject, description}
TaskGet   {id}
TaskUpdate {status, blocks, blockedBy}
TaskList

# state
/tasks/<session>/… via a Backend

The root would see two ways to "plan", the Timeline would carry both, and every step pays ~1k tokens of schemas — against the budget this change exists to cut.

Option · in now

A planning tool exists on day one. Cost: the mapping to plan_step_* is speculative until S2 fixes the v2 contract; likely rework.

Option · S2 owns it

S2 defines the events first; plantask becomes the emitter if its model fits (tasks with dependencies), or a thin plan tool is written against the contract.

Recommendation

Out of this change. Spine compatibility is already secured — it is a middleware like any other, added in S2.

Multi-model consequences that are not decisions

Things the spine swap must do because you run several models. Listed so they are seen, not chosen.

F-26 becomes real

Model cache keys on provider + baseURL + model + token-hash on the ADK path. The legacy path keeps the pinned characterization; the follow-up that deletes legacy closes F-26 for good.

One WrapModel per child

Each child builds its own client for its own spec.Model; effort, usage accumulation and the summarizer setting ride that instance. A contracttest case pins "two children on two models, each usage attributed to its own execution".

Verification is mechanical

Task 2.4 = /api/show for the thinking capability + one measured run per pinned model. No guessing which model honours low; the matrix on the previous slide fills itself in.

Model limits already chain

The analyst's window chain (/api/show → model_limits.yaml → 32k) is per model. In-run summarization triggers per run on that model's window — a child on a 32k model compacts earlier than the root on a 128k one.

Non-thinking models are safe

An effort hint on llama3.1:8b is a no-op; a 400 can only come from an unknown value, and the strict frontmatter decode stops that at load time.

Still open (handoff §4)

The operator's research-agent.example.md says tools: [] with the comment "empty = all tools" — the engine reads it as no tools. Fix by hand before the next research delegation; it is not part of this change.

Part 2 · Model routing as part of intent

Not one LLM for everything: the analyst assigns models to the jobs — orchestrator and sub-agents — from the models at its disposal. Your rule: explicit config wins → otherwise intent chooses → otherwise today's default.

R

The orchestrator (root)

Today: the model you selected for the send, else the agent's pin, else a typed refusal. Routing fills the hole when nothing was selected — an ad-hoc /v1/goals call without a model becomes valid.

C

Each sub-agent

Today: the agent's frontmatter model:, else inherit the root's — which is why glm-5.3-flash did everything in the solar run. Routing gives each recommended agent its own pick.

F

Fixed roles

The analyst and the summarizer keep their own chains (D4). The analyst never routes itself — no recursion, no loop; it stays one validated decision (your decision #1).

The shape · one more field in IntentAnalysis v2 
{ "model_assignments": {
    "root":   "ollama/glm-5.3:cloud",                 // source: intent
    "agents": { "research-agent": "ollama/gemini-3-flash-preview:cloud",
                 "builder-agent":  "ollama/qwen3.5:397b-cloud" },
    "reason":  "4 delegations + ward file work → mid-tier generalist; breadth → cheap tool-capable; code → code-strong" } }

Bounded (one per recommended agent), validated by the HOST, never fatal: an invalid pick falls to the next precedence level and shows up as a drop reason on the analysis card — the drops list already exists.
